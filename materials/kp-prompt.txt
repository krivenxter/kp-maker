Ты — senior full-stack engineer и архитектор внутренних B2B-инструментов.

Нужно спроектировать и реализовать внутреннее веб-приложение Calltouch для генерации персонализированных коммерческих предложений для клиентов.

Это НЕ AI presentation generator.

Главный принцип проекта:

FORM DATA
→ NORMALIZED PROPOSAL JSON
→ STRICT VALIDATION
→ TEMPLATE SELECTION
→ PPTXGENJS RENDERER
→ PPTX
→ optional PDF conversion

80–90% системы должны быть полностью детерминированными.
ИИ может использоваться только как необязательный текстовый enhancer примерно для 10–20% контента и не должен иметь никакого отношения к расчетам, структуре тарифов, позиционированию элементов, дизайну, выбору координат или генерации PPTX.

Перед началом работы:

1. Просканируй весь существующий проект.
2. Изучи приложенные PDF-референсы коммерческих предложений Calltouch.
3. Если в проекте присутствуют старые generator-function.py, metaprompt, kp_metaprompt и другие эксперименты — изучи их как контекст, но НЕ копируй старую архитектуру LLM → HTML → PDF.
4. Составь краткий architecture plan.
5. После этого приступай к реализации MVP.
6. Если README устарел — обнови его.
7. Все API keys, пароли и credentials должны находиться только в .env / environment variables. Никогда не хранить секреты в source code и никогда не отправлять их во frontend bundle.


==================================================
1. ЧТО МЫ СТРОИМ
==================================================

Внутреннее веб-приложение для менеджеров по продажам и аккаунт-менеджеров Calltouch.

Менеджер открывает страницу, заполняет простую форму, выбирает клиента, продукты, параметры проекта, цены, условия, кейсы и себя как контактное лицо.

После заполнения система:

1. нормализует данные;
2. строит Proposal JSON;
3. валидирует каждое поле;
4. автоматически выбирает подходящие варианты слайдов;
5. подставляет контент из заранее подготовленных баз;
6. показывает превью;
7. генерирует нативный редактируемый PPTX;
8. при наличии настроенного PDF backend позволяет скачать PDF.

Результат должен выглядеть как вручную задизайненное коммерческое предложение, но собираться за несколько минут.


==================================================
2. ОСНОВНОЙ ПРИНЦИП АРХИТЕКТУРЫ
==================================================

НЕ генерировать презентацию через HTML → screenshot → PPTX.

НЕ делать слайды картинками внутри PPTX.

НЕ просить LLM писать HTML или JS презентации.

PPTX должен собираться непосредственно через PptxGenJS:

- text → native PPTX text;
- shapes → native PPTX shapes;
- tables → native PPTX tables/shapes;
- images → PPTX images;
- hyperlinks → настоящие ссылки;
- весь важный текст должен оставаться редактируемым.

Использовать одну декларативную модель данных ProposalDocument.

Layout каждого варианта слайда описывается кодом заранее.

Пример:

renderCoverSlide(pptx, proposal)
renderProjectContextSlide(pptx, proposal)
renderConfigurationSlide(pptx, proposal)
renderPricingSlide(pptx, proposal)
renderSolutionFlowSlide(pptx, proposal)
renderCasesSlide(pptx, proposal)
renderContactsSlide(pptx, proposal)

Внутри каждого renderer могут быть layout variants:

cover_known_brand
cover_neutral_brand

configuration_1_product
configuration_2_products
configuration_3_products
configuration_4_products

pricing_single
pricing_comparison_2
pricing_comparison_3

cases_2
cases_3

и т.д.

Количество layout-вариантов ограничено и контролируется разработчиком.


==================================================
3. ТЕХНОЛОГИИ
==================================================

Предпочтительный стек MVP:

Frontend:
- React
- TypeScript
- Vite
- CSS Modules или обычный структурированный CSS
- Zod
- React Hook Form

Presentation engine:
- PptxGenJS

State:
- обычный React state/context;
- Zustand использовать только если действительно понадобится.

Backend для MVP:
- небольшой Node.js + TypeScript service.

PDF:
- PPTX является source of truth;
- PDF желательно получать конвертацией готового PPTX через LibreOffice headless;
- backend должен запускаться в Docker-контейнере;
- POST /api/export/pdf принимает Proposal JSON или созданный PPTX и возвращает PDF.

Если PDF-конвертация сильно усложняет первый MVP:
- сначала полностью реализовать PPTX;
- PDF вынести в отдельный adapter;
- архитектура должна позволять подключить его позднее без переписывания генератора.

Не использовать тяжелый backend без необходимости.
Не использовать БД в первом MVP, если статических JSON/assets достаточно.

4. UX: ИНСТРУМЕНТ ДОЛЖЕН БЫТЬ ПРОСТЫМ
==================================================

Это не дизайнерский редактор.

Менеджер не должен:
- двигать блоки;
- выбирать размеры шрифтов;
- менять координаты;
- выбирать шаблон каждого блока;
- верстать таблицы;
- загружать собственную фотографию;
- вручную вставлять логотип Calltouch;
- думать о дизайне.

Интерфейс должен максимально уменьшать вероятность получить уродливое КП.

Сделать пошаговый wizard примерно из 4 этапов:

ШАГ 1
Клиент и менеджер

ШАГ 2
Задача, продукты и параметры проекта

ШАГ 3
Расчет и коммерческие условия

ШАГ 4
Кейсы, проверка и экспорт

Справа на desktop можно показывать масштабированное preview текущего слайда/всей презентации.

На маленьких экранах preview можно вынести отдельной вкладкой.

Продвинутые и редко используемые поля спрятать в "Дополнительные настройки".

Показывать прогресс заполнения.

Использовать понятные human-readable названия вместо внутренних ID.

Хранить черновик в localStorage.

Добавить:
- "Заполнить демо-данными";
- "Очистить";
- "Скачать PPTX";
- "Скачать PDF";
- "Скачать JSON";
- "Загрузить JSON".

Proposal JSON должен позволять позднее повторно открыть старое КП.

==================================================
13. ПОЛНАЯ ЦЕНА VS ЦЕНА СО СКИДКОЙ
==================================================

Менеджер должен иметь возможность выбрать режим:

1. показывать только итоговую цену;
2. показывать две цены:
   - Полная стоимость
   - По акции / С учетом скидки

Например:

                Полная      По акции

ПО              20 000       15 000
Связь            7 000        5 000

Система сама считает скидку.

Не заставлять менеджера вручную вводить одновременно:
price,
discount,
final price.

Достаточно любых двух величин.

16. УСЛОВИЯ ПЕРЕАДРЕСАЦИИ / ЮРИДИЧЕСКИЕ ТЕКСТЫ
==================================================

Все формулировки про:

- переадресацию;
- включенные минуты;
- стоимость минуты;
- SIP;
- 8800;
- НДС;
- период выставления счета;

считать legal/config data.

AI НИКОГДА НЕ РЕДАКТИРУЕТ эти тексты.

Создать legalTerms.json с version.

Например:

{

    "template": "...",
    "rates": {...}

Например:

а итоговая фраза собирается кодом.

Это позволит юридическому/продажному отделу позже поменять одну формулировку во всей системе.

17. AI — ТОЛЬКО ОПЦИОНАЛЬНЫЙ TEXT ENHANCER
==================================================

В первой версии приложение должно полностью работать БЕЗ AI.

Создать interface:

TextEnhancer

и реализацию:

NoopTextEnhancer

Позднее можно подключить:

OpenAITextEnhancer
GeminiTextEnhancer

AI разрешено обрабатывать только заранее определенные поля.

Например:

raw manager input:

"хотят понимать окупаемость рекламы, сейчас битрикс и звонки"

AI может вернуть:

{
  "projectInsight":
    "Клиенту важно связать рекламные расходы, обращения и продажи в Битрикс24, чтобы видеть окупаемость каналов.",

  "productReason":
    "...",

  "coverSubtitle":
    "..."
}

AI запрещено:

- менять цены;
- считать скидки;
- придумывать метрики;
- придумывать кейсы;
- добавлять продукты;
- придумывать продуктовый функционал;
- менять юридические формулировки;
- выбирать PPTX layout;
- задавать CSS;
- задавать координаты;
- писать HTML;
- генерировать сам PPTX.

Каждый AI output обязательно проходит Zod validation.

У AI должны быть ограничения длины.

Если AI недоступно или output invalid:
использовать исходный менеджерский текст.

Приложение не должно зависеть от AI.


==================================================
18. НЕ НУЖНЫ "AI-КЛАССЫ"
==================================================

Не просить AI определять CSS classes или design tokens для текста.

JSON должен описывать СМЫСЛ текста:

headline
subtitle
body
metric
note
price
legalText
benefit

А template renderer уже знает визуальный стиль каждого semantic slot.

Например:

{
  "type": "metric",
  "value": "+34%",
  "label": "..."
}

Renderer сам понимает:
- font;
- size;
- color;
- position.

Content и presentation должны быть разделены.


==================================================
19. ВАЛИДАЦИЯ
==================================================

Система должна валидировать не только наличие поля, но и пригодность контента для layout.

У каждого текстового slot должны быть ограничения.

Например:

coverTitle:
max 60 chars

coverSubtitle:
max 130 chars

productCardTitle:
max 45 chars

productReason:
max 140 chars

caseDescription:
max 150 chars

benefitTitle:
max 50 chars

benefitDescription:
max 120 chars

Не обрезать текст молча.

Если текст слишком длинный:
- показать ошибку;
- предложить сократить;
- при включенном AI дать кнопку "Сократить".

Но layout не должен автоматически превращать 34pt в 11pt ради того, чтобы впихнуть текст.

Использовать заранее разрешенные typography variants, например:
normal / compact.

Перед экспортом запускать:

validateProposal()
validatePricing()
validateSlideContent()
validateAssets()

При ошибках PPTX не генерировать.


==================================================
20. ПЕРСОНАЛИЗАЦИЯ КЛИЕНТА
==================================================

Персонализация должна быть аккуратной.

Не превращать КП в презентацию клиента.

Calltouch остается основным брендом.

Для известных брендов использовать:

- client logo;
- один accent color;
- hero image;
- возможно heading font из whitelist.

Не применять клиентские цвета ко всем элементам.

Пример:
Calltouch structure + 15–30% visual accent клиента.

На титульном слайде можно использовать клиентский hero.

На внутренних слайдах:
логотип клиента небольшой;
акцентный цвет клиента;
Calltouch typography/grid сохраняется.

Если бренд неизвестен:
использовать фирменный Calltouch visual mode.


==================================================
21. МЕТРИКИ НА ТИТУЛЬНОМ СЛАЙДЕ
==================================================

На обложке желательно 2–3 сильных benefit / metric блока.

Но AI НЕ ИМЕЕТ ПРАВА придумывать цифры.

Источник может быть только:

1. manager-provided metric;
2. approved product metric из products.json;
3. approved case metric;
4. заранее утвержденная industry metric.

Каждая metric должна иметь source.

Например:

{
  "value": "96%",
  "label": "...",
  "sourceType": "product",
  "sourceId": "calltracking"
}

Если подтвержденных цифр нет:
использовать текстовые benefit cards без выдуманных чисел.

23. СРАВНИТЕЛЬНЫЕ МАТРИЦЫ
==================================================

Не хранить сравнительную таблицу как HTML.

Например:

{
  "features": [
    {
      "id": "...",
      "title": "...",
      "values": {
        "basic": true,
        "advanced": true,
        "premium": true
      }
    },

    {
      "id": "...",
      "title": "Хранение звонков",
      "values": {
        "basic": "1 месяц",
        "advanced": "2 месяца",
        "premium": "6 месяцев"

    }
  ]
}

Renderer сам превращает это в PPTX matrix.

Значения могут быть:

true
false
string
number

Не использовать в data layer символы ✓ / —.

Renderer решает, как их визуализировать.

36. ACCEPTANCE CRITERIA MVP
==================================================

MVP считается готовым, если:

1. Можно открыть веб-приложение.
2. Можно заполнить КП без знания дизайна.
3. Можно выбрать менеджера.
4. Можно выбрать 1–5 продуктов.
5. Можно задать параметры проекта.
6. Можно построить pricing с ПО/связью.
7. Можно разделить ежемесячные и разовые платежи.
8. Можно задать полную цену и цену со скидкой.
9. Все totals вычисляются автоматически.
10. Можно выбрать кейсы.
11. Есть preview 7 слайдов.
12. Validation не позволяет экспортировать заведомо сломанное КП.
13. Генерируется настоящий editable PPTX.
14. Текст в PPTX остается текстом.
15. Ссылки остаются кликабельными.
16. Ни один текстовый блок не выходит за границы слайда.
17. Нет placeholder content.
18. Нет invented content.
19. AI можно полностью отключить, и приложение продолжает работать.
20. Proposal можно экспортировать/import как JSON.
21. Есть демо-пример, который можно сгенерировать одним кликом.
22. Проект запускается по README.

==================================================
38. КРИТИЧЕСКОЕ ПРАВИЛО
==================================================

Не превращай проект в "AI делает презентацию".

Это генератор на заранее подготовленной дизайн-системе.

AI — максимум редактор отдельных текстовых формулировок.

Если задачу можно решить обычным TypeScript — решай TypeScript.

Если значение можно вычислить — вычисляй.

Если текст существует в базе — бери из базы.

Если layout известен заранее — используй renderer.

Если факта нет — не придумывай.

Цель проекта:

одинаково качественные коммерческие предложения,
которые менеджер Calltouch может собрать за 3–5 минут,
не имея дизайнерских навыков.
